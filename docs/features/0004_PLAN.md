# 0004 – Notifikace (persistentní v databázi)

## Popis

Systém notifikací ukládaných do databáze. Uživatel po přihlášení (i po dlouhé době) vidí historii oznámení – např. že jeho článek byl schválen, zamítnut, že dostal komentář, lajk u komentáře nebo nového sledujícího.

**Požadavky uživatele:**
- Notifikace se musí ukládat do databáze
- Uživatel po dlouhé nepřítomnosti musí vidět oznámení (např. „váš článek byl schválen“)
- Historie oznámení musí zůstat zachována

---

## Fáze 1 – Datová vrstva

### 1.1 Tabulka `notifications`

Nový SQL skript `docs/sql/create_notifications.sql`:

| Sloupec | Typ | Popis |
|--------|-----|-------|
| `id` | UUID | PK, default `gen_random_uuid()` |
| `user_id` | UUID | Příjemce (FK na users.id) – NOT NULL |
| `type` | TEXT | Typ: `article_approved`, `article_rejected`, `comment_new`, `comment_like`, `new_follower` |
| `title` | TEXT | Krátký nadpis (např. „Článek schválen“) |
| `body` | TEXT | Doplňující text (např. název článku) |
| `link` | TEXT | URL pro proklik (např. `/clanek/slug`) |
| `metadata` | JSONB | Flexibilní data (article_id, actor_id, comment_id, …) |
| `read_at` | TIMESTAMPTZ | NULL = nepřečteno |
| `created_at` | TIMESTAMPTZ | default `now()` |

Funkce: `create_notification(user_id, type, title, body, link, metadata)` – volitelná helper pro PostgreSQL triggery.

Indexy: `(user_id)`, `(user_id, created_at DESC)`, `(user_id, read_at)` pro rychlé dotazy.

### 1.2 RLS politiky (`docs/sql/rls_policies.sql` nebo nový soubor)

- `SELECT`: pouze `auth.uid() = user_id` – uživatel vidí jen své notifikace
- `INSERT`: pouze service role / admin (API routes používají admin klient)
- `UPDATE`: pouze `auth.uid() = user_id` – uživatel může označit jako přečtené
- `DELETE`: volitelně – zatím nepotřeba (historii zachováváme)

### 1.3 Typy (`src/types/database.ts`)

```typescript
export type NotificationType =
  | "article_approved"
  | "article_rejected"
  | "comment_new"
  | "comment_like"
  | "new_follower";

export interface Notification {
  id: string;
  userId: string;
  type: NotificationType;
  title: string;
  body: string;
  link: string | null;
  metadata: Record<string, unknown> | null;
  readAt: Date | null;
  createdAt: Date;
}
```

## Fáze 2A – API Endpoints

### 2A.1 GET `/api/notifications` – Seznam notifikací

- Autentizace: povinná
- Query: `?limit=20&offset=0&unreadOnly=false`
- Načte notifikace pro `auth.uid()` z tabulky `notifications`
- Řazení: `created_at DESC`
- Vrací: `{ items: Notification[], total: number }`

### 2A.2 PATCH `/api/notifications/[id]/read` – Označit jako přečtené

- Autentizace: povinná
- Ověření: `notification.user_id === auth.uid()`
- UPDATE: `read_at = now()` pro danou notifikaci
- Vrací: `{ ok: true }`

### 2A.3 POST `/api/notifications/read-all` – Označit všechny jako přečtené

- Autentizace: povinná
- UPDATE: `read_at = now()` pro všechny notifikace uživatele kde `read_at IS NULL`

### 2A.4 GET `/api/notifications/unread-count` – Počet nepřečtených

- Autentizace: povinná
- COUNT kde `user_id = auth.uid()` AND `read_at IS NULL`
- Vrací: `{ count: number }`

## Fáze 2B – Vytváření notifikací (trigger body)

Centrální helper `src/lib/notifications.ts`:

```typescript
// createNotification(adminClient, { userId, type, title, body?, link?, metadata? })
```

Volán z API routes po úspěšné akci. Nejedná se o PostgreSQL trigger – volání z aplikace.

### Místa volání

| Soubor | Akce | Příjemce | Typ | Příklad |
|--------|------|----------|-----|---------|
| `src/app/api/admin/articles/[id]/approve/route.ts` | Článek schválen | `article.author_id` | `article_approved` | title: „Článek schválen“, body: název článku, link: `/clanek/{slug}` |
| `src/app/api/admin/articles/[id]/reject/route.ts` | Článek zamítnut | `article.author_id` | `article_rejected` | title: „Článek zamítnut“, body: název článku, metadata: `{ reason }` |
| `src/app/api/articles/[id]/comments/route.ts` (POST) | Nový komentář | autor článku (nebo autor parent komentáře u odpovědi) | `comment_new` | body: název článku, link: `/clanek/{slug}`, metadata: `{ article_id, comment_id, actor_id }` |
| `src/app/api/comments/[id]/like/route.ts` (POST při like) | Lajk komentáře | autor komentáře | `comment_like` | body: název článku, link: `/clanek/{slug}`, metadata: `{ comment_id, actor_id }` |
| `src/app/api/users/[id]/follow/route.ts` (POST) | Nový sledující | `targetUserId` | `new_follower` | body: nickname sledujícího, link: `/profil/{nickname}`, metadata: `{ follower_id }` |

**Poznámky:**
- U approve/reject: načíst článek včetně `slug` a `author_id` před vytvořením notifikace
- U komentáře: neposílat notifikaci autorovi, pokud komentuje sám sebe
- U lajku: neposílat, pokud lajkuje sám sebe
- U follow: neposílat sobě ( již validováno v API)

## Algoritmus pro komentáře (kdo dostane notifikaci)

1. Nový komentář (root, `parent_id` = null): notifikace → autor článku
2. Odpověď na komentář (`parent_id` nastaven): notifikace → autor parent komentáře

V obou případech: pokud `author_id === recipient_id`, notifikaci nevytvářet.

---

## Algoritmus pro načtení slug článku

Pro approve/reject/comment: článek má sloupec `slug`. Načíst při dotazu:

```sql
SELECT id, author_id, slug, title FROM articles WHERE id = ?
```

Pro link: `/clanek/${slug}`

Pro komentář: v metadata je `article_id`, načíst článek podle něj pro slug.
